## Learning goal

Establish reference behavior, explicit invariants, reproducible workloads, trustworthy timing, and useful-service metrics from the start. Explain performance with CPU/GPU timelines and kernel profiles, then validate whether changes improve complete requests without violating correctness, quality, ownership, or service objectives.

Module 9 is a required cross-cutting foundation for Modules 1–7: use its relevant chapters alongside the earliest builds and throughout subsequent development. The existing [learning approach](learning-approach.md) applies throughout.

## Metric contracts to establish

| Metric | Required boundary or accounting rule |
| --- | --- |
| TTFT | Request arrival to first token, including queueing; distinguish server and client observation boundaries and first bytes from actual tokens |
| Inter-token latency | Gaps between consecutive token events; distinguish generation, delivery, and streamed chunks; report per-request and pooled populations explicitly |
| End-to-end latency | Request arrival to a defined terminal completion event; separately record failure, cancellation, and timeout outcomes |
| Throughput | Completed requests or useful output tokens per declared time window; keep prompt tokens, speculative drafts, failures, and partial outputs distinct |
| Goodput | Useful completed work meeting a declared correctness/quality and latency predicate per time window; state the objective, unit, and eligible population |
| Memory | Weights, unique live KV blocks, retained prefixes, workspace, communication and staging buffers, allocator reservations, peaks, and fragmentation without double-counting |

For an individual request, use **TTFT = first-token time − arrival time**, **ITL_i = token time_i − token time_(i−1)** for consecutive tokens after the first, and **end-to-end latency = completion time − arrival time**. Use compatible clocks and the same declared observation boundary. A request with no token has no observed TTFT; account for its outcome rather than substituting zero or dropping it silently.

Client-visible streamed chunks may contain multiple tokens. Without token-level instrumentation, report chunk gaps rather than claiming to have measured individual-token delivery times. Open-loop tests must record intended arrivals, actual submissions, generator lag, and outcome counts so a slow server or client does not silently lower the offered load.

## How chapters will be developed

Every chapter follows **Concepts → Experiments → Verification**, applying all [six dimensions and eight engineering principles](learning-approach.md). Connect the evidence to systems engineering and High-Frequency Trading concerns such as latency distributions, timestamp validity, bounded queues, reproducible arrivals, ownership, overload, and recovery. State the limits of each analogy.

Matching generated text alone is insufficient evidence. Validate logits using justified tolerances, distributions using appropriate statistical checks, cache reuse using computation identity, and lifecycle behavior using state and ownership invariants. Sanitizers and finite test sets provide bounded evidence, not a proof that all concurrency or memory errors are impossible.

Benchmark across context length, output length, arrival pattern, prefix-sharing rate, and operating point. Preserve rejected, failed, cancelled, timed-out, and unfinished outcomes in the report. Keep instrumentation overhead, warmup, cold-start work, cache state, uncertainty, and measurement-window effects visible. This module contains outlines only; no load generator, correctness suite, integrated engine, or benchmark result has been produced.
